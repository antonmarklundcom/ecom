## Resulting contracts

Password recovery and transactional email have a separate [proposal](PASSWORD-RECOVERY-EMAIL-PROPOSAL.md), with no enabled sender or operational delivery claim.

The missing mechanisms are implemented in this branch; existing visibility, role, import-preview, inventory, payment/order and backup guarantees remain the foundation. Validation is recorded below before merge. Password recovery and transactional email are deferred proposals, with no operational claim.

- Nullable product `specifications` and private `supplierDetails`; nullable variant `attributes` and verified `identifiers`; product/category SEO overrides. Old rows remain valid. Public projections require valid, non-future verification dates and reject private fields. Supplier references and source URLs never enter storefront props, comparison, feeds or JSON-LD. A private image-provenance flag can label illustrative assets; illustrative images are omitted from merchant feeds and structured product photos.
- Specifications accept optional `unit`, `verifiedAt` and `values`; attributes accept optional `verifiedAt` and `values`. Values are bounded scalar records. Verification timestamps accept ISO offsets and normalize to UTC. Identifiers require verification and a real MPN or checksum-valid GTIN; no identifiers are generated from SKUs. Example: `{"unit":"unidad","verifiedAt":"2026-01-01T00:00:00Z","values":{"capacity":500}}`.
- Optional CSV columns: `specifications`, `supplier_details`, `attributes`, `identifiers`, `seo_title`, `seo_description` (Spanish aliases also supported). JSON errors identify the input line and field. Omitted/blank optional JSON fields preserve stored metadata; JSON `null` explicitly clears it. Preview and apply revalidate ownership/history conflicts. Existing inventory is preserved unless the established explicit stock-reset option is used. Completeness is advisory and does not publish products or authorize orders.
- Store-owned `src/config/catalogue.ts` defines optional facts, filters, comparison and editorial sections/FAQ/guides. Default definitions are empty and comparison limit is three, bounded to two–four. Configure a non-jewellery dimension such as variant `color`, or product `capacity`. Filters use `atributo.KEY` and `stock=1`; unknown/repeated/unbounded input fails closed. All chosen variant dimensions must belong to one actual active variant. Stock uses signed subtraction, unexpired held reservations and UTC. Categories read fresh data; their nonce/CSP policy changes with that dynamic rendering. Filter combinations are noindex, with the base-category canonical.
- Product H1 stays descriptive; SEO overrides change title/description only. `?variante=SKU` chooses the exact active SKU on server and client, including an out-of-stock SKU with buying disabled. Invalid selections receive a notice. Product canonicals always use the current clean product URL; parameterized product URLs are noindex/follow. Offer URLs and feed links carry the actual SKU. ProductGroup requires at least two variants with a configured, verified, genuinely differing schema.org dimension on every member. Otherwise Product is retained. Offers require positive integer prices and purchasable mode; approved reviews remain the only ratings source.
- Current and historical product slugs share `product_slug_redirects` with one unique owner. Transactions claim both old and new names; racing conflicts roll back. Historical names cannot be reused while the product exists, even by that product, preventing cycles. Aliases resolve directly to the current visible product. Inactive products/categories and deleted products return 404. Next.js `permanentRedirect` returns **308**; aliases are not a second sitemap entry.
- Gallery thumbnails, zoom, arrow keys, Escape, focus return and responsive alt text share one component. Ordinary no-photo placeholders remain available. Modal animations respect reduced motion. Image provenance must be supplied honestly by each store.
- Payment precedence: explicit owner setting > `STORE_PAYMENT_METHODS` > store-owned `src/config/checkout.ts`. Template policy remains transfer, cash on delivery and card. Explicit empty/invalid policy closes checkout; transfer requires usable bank details and card requires the provider. Server checkout rechecks readiness. UI selection does not replace payment verification, stock reservation or order transitions.
- Setup requires matching password confirmation on client/server, offers independent visibility controls, focuses the result and hands off to the welcome/guide pages. Reinitialization can replace an existing owner's password, promote/reactivate the account and revoke prior sessions. Demo products are fictitious, opt-in and need removal before real sales. Sidebar choices are role-filtered on the server; saved ordering cannot grant a destination. Save/Cancel/Restore and drag/arrow controls persist per user/site/browser only. Public shopping controls are hidden in admin; the cart sheet does not render there. Print rules preserve the remito's own header.
- Optional `src/config/editorial-tools.ts` supplies an empty, disabled keyword-planning dataset. Only owners (the existing `usuarios` capability) can open `/admin/seo`; disabled tools return 404. Admin remains private/noindex. Coverage means an editorial planning mark, never measured rankings or traffic. No jewellery dataset, synonyms or supplier records are included.

## Migration and recovery

The home skeleton now lives inside the home page. A root `loading.tsx` sends HTTP 200 before descendant product/category pages can decide their 308 redirects or 404s. Existing stores with a customized root loading boundary must remove or narrow it as part of the reviewed update.

`0023_lucky_black_widow.sql` was generated against this template's own `0022` snapshot, then extended with a current-slug backfill. Apply the committed migration and schema extras before starting code that reads the new columns. Do not use `db:push` on production or let two application versions edit slugs during migration. Deployment must provide an explicit maintenance/migration step; deploying this code against an unmigrated database is not safe. No production migration is performed by this PR.

Backups include the nullable columns and `product_slug_redirects`, paginated by slug. Format-2 hashes and snapshots still identify the schema that made a backup. Restore an older supported format-2 backup into a brand-new empty recovery database, load its original schema/rows first, and then run remaining migrations (including the current-slug backfill). A recovery target newer than the backup is deliberately rejected. The legacy format remains explicit opt-in and cannot restore secrets without the matching session secret. Never reset a live catalogue as a verification step.

Health keeps its existing HTTP-200/boolean contract and adds `catalog`: monitors must require `db` and `catalog` to be true, and check `cron` separately. It exercises real catalogue queries and dependent columns even in an empty store. Failures expose no SQL/credentials. Merchant feed failures return 503 with no-store and Retry-After; only the exact missing-FULLTEXT-index error permits LIKE fallback.

## New and existing stores

`nueva-tienda` and `bootstrap:repo` inherit generic code, migrations, optional default config and tests from the committed template. Branding, assets, categories, catalogue rows and verification evidence remain each store's work. A neutral generated-store validation uses synthetic configuration and disposable databases; generated secrets are never PR assets.

Existing stores receive a reviewed `template:sync` update, not a deployment or database copy. The existing three-way merge keeps store-owned `src/config`, branding/content/assets and customized mixed UI. Newly introduced optional config defaults travel when absent; an existing customization stays owned by its store. Changed customized product/category/setup/admin pages must integrate the new components and pass typecheck/test/build before approval. The distribution report explicitly marks `/comparar` and `/setup` as mixed UI, alongside the existing mixed routes. Do not overwrite a custom store page to force compatibility.

Integration checklist for customized pages: pass `initialVariantSku`; use the safe public data projection and SKU offer links; preserve failure-vs-404 handling; resolve slug history before notFound; mount gallery/filter/comparison hooks; expose SEO/metadata fields only behind existing guards; use the new password confirmation payload; keep remito print hooks. Client-rendered admin product rows receive the resolved public thumbnail URL from the server so private Cloudinary settings cannot change their markup during hydration. Review the payment policy and configure optional attributes/editorial data per store. Back up catalogue data before migrations; template sync itself never edits database rows.

## Remaining limitations and per-store work

- Administrator password recovery and transactional email are proposed, not operational. Configure and verify actual bank/provider, image storage, sender, public origin and store identity separately; each store must supply honest facts, identifiers, photos and editorial data.
- The shared storefront shell omits shopping and analytics slots from admin/setup. Account/order tracking and SPA navigation behavior still need a separate privacy review before enabling GA4/Meta; external analytics payloads were not exercised by these isolated checks.
- Apply committed migration/extras before code reads new columns. Restore older backups into a new empty database with their original schema first, then migrate. Existing customized mixed pages require reviewed integration; configuration and branding stay store-owned.
- Health preserves its HTTP-200 boolean contract: a monitor that checks only HTTP status misses failures and must also check `db`, `catalog` and `cron`.
- The existing single-file cloud backup can exceed the provider's per-file limit at large catalogue/order volumes. A future multipart format must include an integrity manifest and refuse partial restores; no limit was reached in these isolated checks.
- The existing Next.js image-chunk CSP exception is covered explicitly by browser tests. Server logs also show "destination stream closed early" during some browser navigations; functional checks pass, but cancellation/log classification remains follow-up work.
- JS budgets pass (home 236.1/247 KB, product 249.4/252 KB, checkout 241.5/246 KB compressed scripts). Product/checkout have limited room for additional client features. The repository's documented major-toolchain upgrade constraints remain in [KNOWN-ISSUES.md](../KNOWN-ISSUES.md); installed versions pass current checks.
