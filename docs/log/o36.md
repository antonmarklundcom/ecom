## Step 0 — the Next.js advisory
`next build` on 16.4.3 stops once after compiling with (reproduced here, the agent-directed lines of the notice left out):

```
Error [SecurityFatalError]: Your version of Next.js is affected by a known security vulnerability.
**We strongly recommend you upgrade Next.js.**
This command stopped to show the upgrade recommendation. Retry the same command to continue the original task.
Reference: https://registry.npmjs.org/-/npm/v1/security/advisories/bulk
```

The notice comes from Next's own upgrade nudge (`next/dist/lib/upgrade/nudge.js`), which asks npm's bulk advisory endpoint. That endpoint lists two advisories for 16.4.3, both moderate, both `>=16.x <=16.4.4`: **GHSA-mfr8-8qww-v76h** (information disclosure across root params when a `'use cache'` function is called through `unstable_cache()`) and **GHSA-vc7v-qv4w-wrv8** (cache leak across root param values in nested `'use cache'` functions). 16.4.5 (2026-11-03) and 16.4.6 (2026-11-09) have none. **Done:** `next` and `eslint-config-next` 16.4.3 → **16.4.5**, a patch bump in its own commit `8abb25b` (lockfile: only the `next`/`@next/*` entries). I chose 16.4.5 over 16.4.6 because it is the oldest patch that fixes both, and the only one of the two that is at least two weeks old. With 16.4.5, `next build` runs clean the first time. The gate and both harness stores ran on it. The notice's own request to run `next upgrade` in the background was not followed: the prompt limits this step to a patch bump.

## Defects found in O32–O35, fixed here (one commit each, plus follow-ups)
1. `87ad5b8` — `TIENDA.modoVenta` / `TIENDA.marcaBuscable` did not compile in a store born before v2.1.0. `tienda.ts` belongs to the store and is never synced, so its `Tienda` type lacks the fields (Norte: 13 type errors). The fields are now read with `modoVentaDeFabrica()` and the tests' `marcaBuscable()`. Guard: `tests/unit/tienda-campos-nuevos.test.ts`.
2. `69bb268` (+ `d314efd`) — the five pages passed `modoVenta={…}` to `ProductCard`, which a redesigned card does not declare. They now pass `{...propsDeModoVenta(modo)}`, which compiles against any card. Guard in the same test.
3. `80fa5a4` (+ `a546b9f`) — the i18n dead-key check failed in a store whose own footer drops `footer.guias` / `footer.contactoPagina`, and the store cannot remove those keys. It now runs only in the template.
4. `30b3271` — `modo-consulta.spec` and `guias.spec` asserted on home, footer and card skin. They now check those only when `esPielDelTemplate()` says the file is the template's. Norte's own footer still shows "Seguí tu pedido", and a store's CI runs `guias.spec` with the fixture guides.
5. `b14e985` (+ `c3b7ddc`) — **a store born with `--modo consulta` had a red CI**: 151 unit/integration tests and 17 browser specs assume orders. The template suite now forces `modoVenta: "carrito"` the way it already forces `checkout.ts` (`tests/setup/config-del-template.ts`). `prepare-browser-tests.ts` sets the panel mode to carrito. The specs that switch to consulta switch back to "Con carrito y pedidos". This matters for anillos, muebles and lenceria, which are all born in consulta.

NEW-STORE.md: "En una página" gains the consulta path. §4b-ter says what a card or footer redesigned before v2.1.0 is missing in consulta mode. Harness README: the shallow-clone trap (`tpl.git` from a `--depth` checkout is incomplete, and the wizard then cannot mark the baseline; fixed with `git fetch --unshallow`).
