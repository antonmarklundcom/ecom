# O24 — a store adopts the template's migration history (2026-11-11)

Opus 5.5. Prompt `fable/prompts/opus-24-adopt-template-history.md`, plan `fable/plan-2026-11.md` §5.6, review F13. Branch `phase/o24-adopt-history`.

## Built
- `pnpm template:adoptar-historial` (`scripts/template-adoptar-historial.ts`): reads the live schema (`information_schema`) and both sides' drizzle snapshots into one normalised map (MySQL 8 and MariaDB shapes), and finds how many template migrations explain the database (must be a prefix). Per template migration: already there → marked applied, not there → pending for `db:migrate`, other definition or half there → refused with every difference and a per-migration summary.
- Store-only objects go to one `NNNN_propias_de_la_tienda` after the template's last: snapshot = template's last + those objects; SQL from drizzle-kit's own generator, each statement wrapped in `PREPARE … IF(object missing)`, so it is a no-op where adopted and creates them in a fresh database.
- `--aplicar`: refuses without a dump of this database from the last hour (`backups/`, `--backup`, or a cron `job_runs` OK); swaps `drizzle/` and rewrites `__drizzle_migrations` (`FOR UPDATE`, compare, delete, insert) in one transaction; any failure rolls back and restores the folder; the next run repairs a killed one from the history rows (exactly the old journal → old `drizzle/` back; already the new one, i.e. killed after COMMIT → keeps it, drops the copy). Never runs DDL. Re-running is a no-op ("ya adoptada").
- Also refuses: database not exactly at the store's own journal, live schema ≠ the store's snapshot (hand edits), a store change to a template object, non-InnoDB history table. Data-only SQL (`UPDATE`) in migrations it marks applied is listed as a warning.
- `template:sync`: an adopted store's journal (template + trailing own entry) no longer conflicts (`journalSinChoque` in `template-migrations.ts`, one hook in the `fusionar` branch); the guard message names the new command.
- Harness store Oeste (`customize.sh oeste`, `populate_oeste.sh`, `adopt_store.sh`, `sync_oeste.sh`); `mk_store.sh` archives without CRLF conversion (f9979ce has no `.gitattributes`); `lib.sh` unsets every inherited `GIT_*`, so the harness's `git init`/`git config` never reach a caller's repo.
- NEW-STORE.md § "Migraciones propias de una tienda": runbook, the rule "a store never runs `db:generate` to port a template fix", and what to do when refused.

## Decisions
- Decide by snapshot-state matching (`live == template snapshot k` over every key the new template migrations touch), not per-migration SQL: it handles chains (a later migration changing an earlier one's column) and needs no scratch database on Hostinger.
- The own migration stays pending when template migrations are pending (marking it applied would make drizzle skip the older template ones); its conditional SQL makes that safe.
- Real mascota/lenceria are refused by design (half of 0018, different default): `docs/decisions-needed.md` §2.
- Outside Owns, both needed for exit lines: a 15-line journal hook in `scripts/template-sync.ts` ("sync completes"), and `tests/integration/catalogue-inheritance.test.ts` now drops the columns its fake 0022 backup cannot know from the 0022 snapshot instead of a hand list (Oeste's `products.pais_origen` made it red in the store; "verify_store green").

- MariaDB, run against 10.11 in CI ("Tests en MariaDB", #181, run 43121103205, 2581 passed / 1 skipped): the first run (43118996858, on #180) had 60 false differences only because the fidelity test read the schema with the flavour fixed to `mysql`; the tool itself detected MariaDB and its Oeste/Mascota cases passed. Fixed in #181: `longtext` is `json` only with its `json_valid(col)` CHECK, which no longer counts as a store check; MariaDB < 10.2.7 (text `'NULL'` default and "no default" read the same) is refused before anything is written. A hand-made `longtext CHECK (json_valid(col))` is indistinguishable from `json` on MariaDB and reads as `json`. Not proven on a server: MariaDB other than 10.11, MySQL < 8.0.13, backslashes in string defaults.
- Hand-written SQL in a template migration that creates objects not in its snapshot cannot be detected.
- Load flake, not O24's code: `tests/integration/order-notifications.test.ts` "manda el aviso…" failed once in #174's first full run (the order row was gone when the notifier read it); it passed alone (6/6), in the full re-run and in the three other full runs of this phase.
