## Verdict

1. **ecom `main` is solid but has run blind since early October**: GitHub Actions is off, no open PR ever had CI, and running the suite as CI would found a real bug on `main` (F1).
2. **The nine foundation PRs are already merged together** on `origin/foundation/integracion`, conflicts resolved; landing them is a verification job with three small corrections (phase O22, today).
3. **productos.new is a catalog-only fork on Workers + D1** that cannot be merged back; it is rebuilt from the template when it needs checkout, and only one fix must travel back (CSV formulas).
4. **Hostinger managed Node holds 10 stores per Cloud plan, 5 on Business** (Hostinger's published cap); hundreds of stores means dozens of plans or a different shape (Q5).
5. **Distribution to stores has never run for real**, and all four live stores now have migrations that collide with the template's (F13): the first sync would stop in every one.
6. Order of work: land (O22) → prove the factory (O23) → reconnect the stores (O24) → scale (O27–S29). First file: `fable/prompts/opus-22-land-foundation.md`.

## Hundreds of stores

### Hostinger limits (fetched 2026-11-10 from hostinger.com/support)

| Plan | Node.js websites | NPROC | RAM | CPU | Databases | MySQL conn. per user |
|---|---|---|---|---|---|---|
| Business / Unlimited | **5** | 120 | 3 GB | 2 | 150 | 75 |
| Cloud Startup | **10** | 200 | 4 GB | 4 | 300 | 100 |
| Cloud Professional | **10** | 400 | 6 GB | 5 | 300 | 125 |
| Cloud Enterprise | **10** | 600 | 12 GB | 6 | 300 | 150 |
| Cloud Enterprise Plus | **10** | 800 | 15 GB | 8 | 300 | 175 |

Sources: "Hostinger Node.js limits for web and cloud plans" and "Parameters and limits of
hosting plans in Hostinger" (plan version v6, default since 2026-09-22). From the same pages:
- NPROC counts every process **and thread** on the plan, shared by all its sites. "One Next.js
  app can use about 10–11 threads", and `domain.tld` and `www.domain.tld` "each run a separate
  process".
- At the limit Node sites return **503** (the repo's notes say 429; productos.new's own notes
  call the cause "suspected, not proven").
- "Older deployments could leave previous copies of the app running. New deployments no longer
  do this." Hostinger also says: do not run cluster mode or PM2, and "avoid starting extra
  child processes from your app".
- A request is cut at 120 s; no always-running workers; no custom ports.
- Agency plans: the limits table says Node is unlimited within resources, but the plan
  comparison article says "Node.JS support: Soon" and "GIT access: No". Treat as not available.

**So one plan holds at most 10 stores** (5 on Business), whatever its RAM. By threads, a Cloud
Startup plan (200) fits about 18 single-hostname apps, or about 9 if `www` and the apex each run
one. The template's `DEPLOY.md` has no rule for `www` (F10). RAM per store is not measured
(guess: 150–300 MB); MySQL is not the constraint (pool of 8 per store, `src/db/index.ts:12`).
The account in the repo's notes ("Max Processes (200) … 9 apps", `next.config.ts:68-71`) looks
like one Cloud Startup plan that is already nearly full with other apps.

100 stores = 10 Cloud plans; 300 stores = 30 plans. Whether one Hostinger account can hold that
many plans, and whether more Node apps per plan can be bought, is **unverified**: ask support.

**Latency Brazil → Paraguay: unverified.** Hostinger lists "Brazil" as a location and names no
city. The only figure found is a hosting company's marketing claim of 30–50 ms Asunción–São
Paulo. Measure it from a phone in Paraguay against a Hostinger URL before relying on it.

### D1 from Node

- Outside Workers, D1 is reachable only through Cloudflare's REST API; Cloudflare's own page
  says that path "primarily interacts with the control plane". Every query would be an HTTPS
  round trip from Brazil. No rate limit is published for it (unverified).
- D1 has no interactive transactions (batches only), so no row locks.
- The template refers to `FOR UPDATE` 66 times across 22 files in `src/` (20 of them under
  `src/domain/**`): orders, stock reservations, payments, receipts, coupons, returns, order
  numbers, job claims, login tokens. **None of that may go to D1.** Nor sessions, rate limits or anything in the
  checkout request path.
- Where D1 could still help, all outside the template and outside any request path: a central
  registry of stores and their health for Anton's own dashboard; an append-only copy of
  cross-store sales events for reporting, pushed by cron; a read-only catalog snapshot for a
  catalog-only site that is not a template store (what productos.com.py is today).
- Recommendation: no D1 in the template. If it is used, only as a write-behind sink.
