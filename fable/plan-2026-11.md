## 3. Scope

- **Land:** the foundation batch, with the three corrections of §5.1.
- **Prove:** the template as a factory with the new foundation (two stores, sync, migration
  collision, backup/restore, clean clone), then a first tagged release.
- **Reconnect the existing stores:** a scripted way for a store to adopt the template's
  migration history (all four live stores collide today).
- **Harden:** CSV formula neutralisation, spreadsheet size limits, dependency refresh.
- **Scale:** measured stores-per-plan on Hostinger, distribution that survives 100+ stores,
  a faster new-store path.
- **productos.new:** make its docs tell the truth now; rebuild it on the template when it
  needs checkout.
- Out of scope: multi-tenant mode, VPS hosting, any Workers/D1 work in ecom (§8, §10).

## 4. Autonomy protocol

1. Work until every exit criterion in the phase prompt passes. Never ask permission for
   in-plan work.
2. **Local gate** (the only gate while Actions is off). With MySQL 8 running:
   `pnpm install --frozen-lockfile && pnpm db:generate` (no diff in `drizzle/`) `&& pnpm
   typecheck && pnpm lint && pnpm test && pnpm build`, with `REQUIRE_DATABASE_TESTS=1` and a
   `TEST_DATABASE_URL` whose database name contains `test`. Phases that touch storefront,
   checkout or admin also run Playwright (`pnpm exec tsx scripts/prepare-browser-tests.ts`,
   then `pnpm exec playwright test`, nothing else using that MySQL). Report real numbers.
   On Anton's PC: MySQL 8.4.11 is unpacked at `C:\dev\tools\mysql\mysql-8.4.11-winx64`; start
   it with the command in `fable/REVIEW-2026-11-10.md` § "How this was tested" (port 3317,
   root/root, server time zone −03:00 like CI). The PC's own time zone is America/Asuncion:
   the suite must pass there, not only with `TZ=UTC`.
3. One PR per phase, branch `phase/<id>-<slug>` off latest `main` (O22: off
   `foundation/integracion`). Merge it yourself when the gate is green; merge commit, not
   squash. A red gate is always this session's own work.
4. Minor issues → the phase log's "Known issues". Stop and ask ONLY for a missing credential
   with no graceful fallback, or a bad-foundation decision (schema, auth, money, order states,
   deploy contract). "Ask" = append to `docs/decisions-needed.md`, commit, push, end the
   session.
5. Missing env/config never blocks: document in `docs/ENV-OPCIONAL.md`, degrade gracefully.
6. Prompts are re-runnable: check the branch first, continue from the first unmet criterion.
   WIP commit at least every 30 minutes.
7. Sonnet phases: no changes under `src/domain/**`, `src/db/schema.ts`, `drizzle/**`,
   `src/app/actions/**`, checkout or auth. If the fix needs one, write it to the phase log's
   Backlog line and stop short of it.
8. **Model cost guardrail.** Fable / Mythos-class models are never used for a phase, a
   subagent, a spawned session, a watcher or a Routine. Phase tables name Opus and Sonnet
   only. A session that believes it needs Fable writes why to `docs/decisions-needed.md` and
   ends. Subagents: Sonnet for normal work, Haiku for mechanical fan-out, set explicitly.
9. **File ownership.** A phase writes only to its `Owns` column, plus its own
   `docs/log/<phase>.md`, new tests for its own change, and `CHANGELOG.md` § "Sin publicar".
   On conflict with `main`: main wins, re-apply your change, re-run the gate.
10. **Handoff.** Done = PR merged, exit checklist passed, ONE re-run of the gate on `main`,
    ONE adversarial re-read of the merged diff (fix findings in one follow-up commit), phase
    log committed. Then spawn the next phase with `create_session` (model set explicitly per
    the table, never `plan` mode, prompt exactly `Read fable/prompts/<file>.md in this repo
    and execute it.`). If `create_session` is unavailable, or the next phase needs a §7 input
    that is missing, stop and report.
11. **Phase log:** `docs/log/<phase>.md`, ≤ 12 lines Built, ≤ 8 Decisions, ≤ 8 Known issues,
    one Verification line with commit and test counts. Add the index line to §9.
12. **Orientation read:** the prompt file, §1 and §4 of this plan, the phase's own section,
    the table, §9, and the logs of the phases it depends on. Not the old plans.
13. No production changes by any phase: no DNS, hPanel, Cloudflare, D1, R2 or live database
    writes, unless the prompt names the exact change and §7 shows Anton approved it.
14. Decisions travel by files: to change a phase, edit its prompt on `main`. Nobody messages
    a running session. No session supervises another live.

### 5.6 O24 — a store adopts the template's migration history

Review F13: mascota, lenceria, anillos and productos.new each generated migrations of their
own under numbers the template also uses, mostly while porting template fixes by hand. The
sync guard stops them (correctly) and the only way out today is a manual procedure.
1. Harness store "Oeste", shaped like mascota: baseline `f9979ce`, then two store-made
   migrations that duplicate what the template's `0011`/`0012` and later ones do.
2. `pnpm template:adoptar-historial` (run in the store): dry-run by default. For each template
   migration it decides from the live schema whether its effect is already there (mark as
   applied), not there (stays pending for `db:migrate`), or there with a different definition
   (refuse and print the difference). Store-only columns and tables are kept and moved into
   one new store migration numbered after the template's last. It refuses without a backup
   made in the last hour. With `--aplicar` it replaces the store's `drizzle/` with the
   template's, appends the store-only migration, and rewrites `__drizzle_migrations` in one
   transaction.
3. Proof: Oeste before/after has an identical data fingerprint (`snapshot.py`), `db:check`
   clean, sync to `main` completes, `verify_store.sh` green. A store whose schema does NOT
   match is refused with the exact differences.
4. NEW-STORE.md gets the runbook and the rule: a store never runs `db:generate` to port a
   template fix; it syncs. No phase runs this against a live store database: Anton approves
   that per store, after a backup.
